# COT: Telemetry Interpretation Guide

This document defines how the AI Skill should interpret the pre-parsed JSON telemetry payload generated by Python's `TelemetryParser`. 

**Note:** The Python parser already handles the raw log parsing (regex, log format extraction). This COT is strictly for *interpreting* the resulting JSON structure to find anomalies.

## The Telemetry Payload Structure

The `telemetry_data` payload will look like this:

```json
{
  "thermal_throttles": [
    {"zone": "cpu-0-thermal", "temp_c": 96.5, "event": "throttle"},
    {"zone": "cpu-1-thermal", "temp_c": 97.2, "event": "throttle"}
  ],
  "cpu_frequency_drops": [
    {"core": 0, "baseline_mhz": 2400, "current_mhz": 1800, "drop_pct": 25.0},
    {"core": 1, "baseline_mhz": 2400, "current_mhz": 1800, "drop_pct": 25.0}
  ],
  "vmstat_anomalies": {
    "context_switches": 75000, 
    "swap_activity": 1500,
    "io_wait_percent": 12.5,
    "free_memory_mb": 120
  },
  "dmesg_anomalies": {
    "oom_kills": ["com.android.chrome", "system_server"],
    "cpu_offline_events": []
  },
  "ftrace_anomalies": {
    "sched_wakeup_latency_us": 1250,
    "migration_count": 85
  },
  "warnings": [
    "No ftrace data found (debugfs locked)"
  ]
}
```

## Interpretation Rules by Category

### 1. Thermal Logs (`thermal_throttles`)
- **What it means:** The device's temperature sensors exceeded hardware-defined critical limits, causing the kernel to forcefully reduce performance to prevent physical damage.
- **Interpretation:** If `count > 0`, this is a **hard hardware bottleneck**. It almost certainly explains any CPU or GPU regression.
- **Nuance:** Distinguish between `cpu-*-thermal` (impacts CPU benchmarks) and `ddrss-*-thermal` (impacts Memory benchmarks).

### 2. CPU Frequency (`cpu_frequency_drops`)
- **What it means:** The clock speed of the CPU cores was lower during the current run than the baseline.
- **Interpretation:** 
  - If paired with `thermal_throttles`, this is **DVFS** (Dynamic Voltage and Frequency Scaling) responding to heat.
  - If NOT paired with thermals, it could be a power governor issue (e.g., battery low) or background workload stealing the high-performance cores.

### 3. Virtual Memory Stats (`vmstat_anomalies`)
- **Context Switches (`context_switches`):** Normal baseline is ~10k-20k/sec. Spikes >50k/sec indicate heavy thread contention. Very relevant for `sysbench_threads` and `osbench`.
- **Swap Activity (`swap_activity`):** Spikes >100k/sec (si+so) indicate memory thrashing. The system is struggling to allocate RAM and is paging out to disk.
- **I/O Wait (`io_wait_percent`):** The percentage of time the CPU spent idle waiting for disk I/O. >30% is a severe bottleneck. Normal for `tiobench`/`fileio`, but abnormal for `coremark` (CPU).
- **Free Memory (`free_memory_mb`):** <50MB is critically low. Look for `oom_kills`.

### 4. Kernel Logs (`dmesg_anomalies`)
- **OOM Kills (`oom_kills`):** The Out-Of-Memory Killer was invoked. This is catastrophic. It means a process (possibly the benchmark itself) leaked memory or requested too much.
- **CPU Offline (`cpu_offline_events`):** The kernel completely disabled a CPU core (usually due to extreme heat or battery conservation). Massively impacts multi-core benchmarks.

### 5. Fast Trace (`ftrace_anomalies`)
*Note: This data is only available if Tier 2 RCA was executed.*
- **Wakeup Latency (`sched_wakeup_latency_us`):** Time between a thread becoming ready to run and actually executing. >5000us (5ms) is high and directly explains latency spikes in `osbench` or `hackbench`.
- **Migration Count (`migration_count`):** Number of times threads were moved between cores. High numbers (>500) destroy L1/L2 cache locality, explaining drops in `bw_mem` or `coremark`.

## Handling Missing Telemetry
If a specific telemetry source is empty (e.g., `ftrace_anomalies` is `{}`), DO NOT assume the metric is healthy. Instead, look at the `warnings` array. If "No ftrace data found" is present, the data couldn't be collected (e.g., debugfs locked). Acknowledge this limitation in the RCA output.
